## Root cause — bypass logic is dead code from the controllers

`RequestHelper.cs` exposes two overloads :

```csharp
// L11 — 2-arg overload, calls 3-arg with configuration=null
public static bool TryExtractJwtToken(HttpRequest request, UserContextInfo userContextInfo, out string errorMessage)
    => TryExtractJwtToken(request, userContextInfo, null, out errorMessage);

// L16 — 3-arg overload, the only one that triggers TryTestBypass
public static bool TryExtractJwtToken(HttpRequest request, UserContextInfo userContextInfo, IConfiguration? configuration, out string errorMessage)
{
    if (configuration != null && TryTestBypass(request, userContextInfo, configuration, out errorMessage))
        return true;
    // ... fallback to Authorization Bearer + Client-Email + Client-Session-Id
}
```

`grep -rn "TryExtractJwtToken" Api/Mail/src` shows :
- 11 call sites in `MailController.cs` — **all** use the 2-arg overload (no IConfiguration)
- `SyncController.cs` — same, 2-arg overload
- Other controllers — same pattern
- **0 call sites pass IConfiguration** to the 3-arg overload

So `TryTestBypass` never executes. The bypass headers are read by no
one. The 400 we observe is the symptom of an unrelated DI issue
(controller construction fails on missing Redis connection — see
the second 400 trace in Seq below).

## Two issues to fix in the codebase

### Issue A — wire the bypass into the controllers

Each controller method (or, better, a custom `[Authorize]`-style
filter / middleware) must pass `IConfiguration` to `TryExtractJwtToken`
so `TryTestBypass` can actually run. Three possible patterns :

1. **Inject IConfiguration in each controller** and pass it explicitly.
   ~50 call sites — boilerplate but mechanical.
2. **Action filter** (`IAsyncActionFilter`) that runs JWT extraction
   centrally and short-circuits with `Unauthorized` when no creds.
   The filter can `[FromServices] IConfiguration` cleanly.
3. **Authentication middleware** that recognises the bypass key as a
   first-class auth scheme, populates `HttpContext.User`, and lets
   the controllers stay agnostic.

Option 2 is probably the smallest diff. Option 3 is the cleanest
long-term.

### Issue B — Aspire api process can't see Redis connection string

Even if the bypass were wired, `MailController`'s constructor injects
`IDraftCacheRepository` which transitively needs the Redis client.
The api process under Aspire AppHost gets HTTP 400 on controller
construction with :

> No endpoints specified. Ensure a valid connection string was
> provided in 'ConnectionStrings:mss-mail-redis' or for the
> 'Aspire:StackExchange:Redis:ConnectionString' configuration key.

Yet `docker ps` shows a healthy `mss-mail-redis-jxsmvzrd` container
provisioned by AppHost. So Aspire's Redis resource is up but the api
isn't receiving the connection string.

Likely cause : `AppHost.cs` declares `var redis = builder.AddRedis(...)`
but the api project line
`builder.AddProject<Projects.mss_mail_api>("mss-mail-api")` is missing
`.WithReference(redis)`. Aspire only injects connection strings when a
project explicitly `WithReference`s the resource.

Verify and fix in `Api/Mail/src/AppHost/AppHost.cs`. Same applies to
RabbitMQ and Postgres if the api consumes them.
